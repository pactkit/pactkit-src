# BUG-029: project-init Stack Detection Fallback Causes CLI Hang

| Field | Value |
|-------|-------|
| ID | BUG-029 |
| Type | Bug |
| Priority | High |
| Release | 1.6.5 |
| Status | Draft |

## Summary

When running `/project-init` on a greenfield project that has no language stack identifier files (`pyproject.toml`, `package.json`, `go.mod`, etc.), Phase 1.3 Stack Detection falls through to "ask the user to specify". This causes Claude Code CLI to hang/freeze because slash commands may not support mid-execution user interaction reliably.

Reproduced 2 times on the `mhigh` project.

## Root Cause Analysis

**File**: `src/pactkit/prompts/commands.py`
**Line**: 601

```markdown
- If none match → ask the user to specify
```

When no stack identifier files exist, the playbook instructs Claude Code to ask the user. However:
1. Claude Code CLI's slash command execution may not support "pause and wait for user reply" mid-flow
2. The playbook's remaining phases (2-7) are queued behind this blocking question
3. This creates a deadlock: Claude is waiting for user input, but the CLI framework may not relay the question or accept the answer

**Contributing factor**: The `pactkit.yaml` already has `stack: auto` set, but the playbook ignores this existing config value and re-detects from scratch.

## Target Call Chain

```
/project-init (playbook)
  -> Phase 1.3: Stack Detection
    -> Check pyproject.toml? NO
    -> Check package.json? NO
    -> Check go.mod? NO
    -> Check pom.xml/build.gradle? NO
    -> FALLBACK: "ask the user to specify" -> ** HANG **
```

## Requirements

### R1: No blocking user input during Stack Detection
The playbook MUST NOT block on user input during Stack Detection when `pactkit.yaml` already has a `stack` value configured.

### R2: Config-first stack resolution
If `pactkit.yaml` exists and `stack` is set (even `auto`), the playbook MUST use that value and skip file-based detection.

### R3: Safe fallback to auto
If no stack can be determined from either config or file detection, the playbook SHOULD default to `auto` and log a warning, rather than blocking for user input.

### R4: Post-init advisory only
The playbook MAY still ask the user to specify stack only AFTER all other phases complete (as a post-init advisory, not a blocking gate).

## Acceptance Criteria

### AC1: Greenfield project with pactkit.yaml stack: auto
Given a project directory with no language stack identifier files and `.claude/pactkit.yaml` exists with `stack: auto`, when `/project-init` is executed, then Phase 1.3 MUST NOT ask the user to specify stack, MUST use `stack: auto` from pactkit.yaml, and the init flow MUST complete through Phase 7 without hanging.

### AC2: Greenfield project with no pactkit.yaml
Given a project directory with no language stack identifier files and no `.claude/pactkit.yaml` exists, when `/project-init` is executed, then Phase 1.3 MUST default to `stack: auto`, MUST log a warning "No stack detected, defaulting to auto", and the init flow MUST complete without hanging.

### AC3: Project with identifiable stack files
Given a project directory containing `pyproject.toml`, when `/project-init` is executed, then Phase 1.3 MUST detect `stack: python` and the init flow MUST complete normally.
