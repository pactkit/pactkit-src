## Background

After a Story runs Plan → Act, attempts to start `project-check` or `project-done` crash with `invalid_workflow_state`, and `pactkit work-unit status <plan-run>` also crashes. Root cause (verified by probing `_validate_finalize_projection_fingerprints` on a real plan run):

`_validate_finalize_projection_fingerprints` (`workflow_engine.py:1063`) re-validates a completed plan run's projections (spec/hld/story/board/context) against disk. It ALREADY tolerates legitimate evolution for **hld** (the `known_hld` set, `:1131-1177`, accepts a changed HLD when another completed Core journal recorded that exact revision) and for **board/context** (matched against the CURRENT canonical render, not a frozen fingerprint). But:

1. **context.md goes stale after a later workflow marks the story done.** Act's `finalize-workflow` writes context.md, but the written content reflects pre-completion counts (e.g. `Done: 6` while the canonical render is `Done: 7`). The context check (`:1181-1191`) compares on-disk context against `generate_context(root, command="pactkit finalize-plan")`; the staleness mismatches → `invalid_workflow_state`. This is a general bug affecting every Plan → Act → (Check|Done) sequence.
2. **`spec` has no tolerance** (`:1121-1130`, strict `_fingerprint(spec) != fingerprints["spec"]`). A spec edited after its plan run finalized (e.g. a self-audit revision) drifts and breaks the plan run. This is partly process discipline (spec edits should happen in the `spec_lint` WorkUnit, before finalize), but the brittleness is real.
3. **Predecessor-lookup scans over-validate.** `_completed_run_for_story` (`:~1670`) reads each scanned run with `_read_scanned_state(validate_completed=True)` (default), re-validating projection fingerprints during a mere existence lookup. So a stale sibling journal — from cause 1, 2, or any other — poisons `project-check`/`project-done` start, blocking the whole PDCA chain. (`_active_runs_for_story` already uses `validate_completed=False`; the asymmetry is the bug.)

The HLD tolerance pattern (`:1131-1177`) proves the system's INTENT is to tolerate legitimate evolution; this story extends that intent to cover the real drift paths and stops predecessor lookups from poisoning the chain.

## Requirements

### R1: finalize-workflow regenerates context.md (and board) to post-completion canonical (MUST)

When a non-Plan `finalize-workflow` completes a Story, it MUST regenerate `docs/product/context.md` (and `docs/product/sprint_board.md`) so they reflect the **post-completion** canonical state (story marked done → counts updated). The on-disk context MUST equal `generate_context(root, command=<finalize command>)` recomputed AFTER the story status flip. This eliminates cause 1 (context staleness) so a completed plan run's context projection stays valid after a later workflow marks the story done.

### R2: predecessor-lookup scans do not over-validate sibling journals (MUST)

`_completed_run_for_story` (and any predecessor/existence scan over run files) MUST read scanned runs with `validate_completed=False` — matching `_active_runs_for_story`. A predecessor EXISTENCE lookup must not re-validate projection fingerprints; that strict validation belongs on EXECUTION reads (`_read` with default `validate_completed=True`), where tamper-detection matters. This stops a stale sibling journal — from any cause — from poisoning `project-check`/`project-done` start. After R2, a stale plan run no longer blocks a later workflow's `start`.

### R3: tamper-detection preserved on execution reads (MUST — security)

R2 only relaxes EXISTENCE-lookup scans. EXECUTION reads (`_read` → `_validate_completed_finalize_journal` → `_validate_finalize_projection_fingerprints`) MUST remain strict: a projection whose current disk fingerprint is NOT explained by any completed Core journal (i.e. genuinely tampered, not legitimately evolved) MUST still raise `invalid_workflow_state`. The hld `known_hld` tolerance pattern (`:1131-1177`) is the reference: unexplained drift rejects, explained drift tolerates. R3 MUST NOT weaken this for execution reads.

### R4: regression test for the full Plan → Act → Check → Done chain (MUST)

A test MUST exercise the real sequence: finalize a Plan run, then finalize an Act run for the SAME story (which overwrites story/board/context), then `start("project-check")` and `start("project-done")` MUST both succeed (no `invalid_workflow_state`) — provided the predecessors exist. Today this sequence crashes; after R1+R2 it must not. This is the acceptance proof that the user-facing blocker is gone for everyone.

## Acceptance Criteria

### AC1: Done/Check start no longer crashes after Act finalization (R2)

- **Given** a Story with a completed Plan run and a completed Act run (Act overwrote story.yaml/board/context)
- **When** `engine.start("project-check", goal=..., story_id=...)` and `engine.start("project-done", ...)` are called (with the required predecessor completed for each)
- **Then** neither raises `invalid_workflow_state`; Check starts (predecessor project-act found) and Done starts (predecessor project-check found)

### AC2: context.md stays canonical after finalize-workflow (R1)

- **Given** a Story finalized via `finalize-workflow` (Act)
- **When** the finalize completes
- **Then** `docs/product/context.md` content equals `generate_context(root, command=<finalize command>)` recomputed post-completion; the context projection of the earlier Plan run validates without `invalid_workflow_state`

### AC3: `status <plan-run>` survives Act finalization (R1)

- **Given** the same sequence (Plan finalized, then Act finalized for the same story)
- **When** `pactkit work-unit status <plan-run-id>` is called
- **Then** it returns the completed state (no crash), because context/board are canonical (R1)

### AC4: tamper-detection intact on execution reads (R3)

- **Given** a completed Plan run, then a MANUAL tamper of `docs/product/sprint_board.md` to a fingerprint no completed Core journal explains
- **When** `engine._read(<plan-run-id>)` (execution read, validate_completed=True)
- **Then** it raises `invalid_workflow_state` (tamper detected — R2 did not weaken execution reads)

### AC5: predecessor lookup uses lenient scan (R2)

- **Given** the implementation diff
- **When** `grep` inspects `_completed_run_for_story`
- **Then** it calls `_read_scanned_state(path, validate_completed=False)` (lenient existence scan), matching `_active_runs_for_story`

### AC6: full-chain regression (R4)

- **Given** the test from R4
- **When** run after the fix
- **Then** Plan → Act → Check → Done `start` calls all succeed without `invalid_workflow_state` (Done may still require the Check predecessor — that's the separate Check-gate design story, out of scope here)

## Target Call Chain

`pactkit work-unit start project-{check,done}` → `WorkflowEngine.start` (`:1518`) predecessor check → `_completed_run_for_story` (`:~1670`, R2: switch to `validate_completed=False`) → today crashes via `_read_scanned_state(validate_completed=True)` → `_validate_completed_finalize_journal` (`:1388`) → `_validate_finalize_projection_fingerprints` (`:1063`) → context check (`:1181-1191`) fails on stale context. R1 fixes the stale-context source in `finalize-workflow` (regen post-completion). R3 keeps `_read`/`_validate_finalize_projection_fingerprints` strict for execution reads.

## Out of Scope

- **spec post-finalize edit tolerance**: a spec edited after its plan run finalized still drifts (spec is strict, `:1121`). The fix here is process discipline — spec edits belong in the `spec_lint` WorkUnit before finalize, or trigger a re-finalize. Extending hld-style tolerance to spec is deferred (no later workflow naturally rewrites spec; the "another journal explains it" pattern doesn't cleanly apply). Tracked as a separate follow-up if friction shows it's needed.
- **Check-gate design (③)**: `project-done` requiring a completed `project-check` (predecessor map) vs CLAUDE.md saying Check is optional — a docs/code contradiction requiring a design decision. Separate story.
- **workflow/work-unit subsystem unification (④)**: `pactkit workflow finish-guard`/`revalidate-artifacts` (workflow namespace) not recognizing work-unit runs. Architectural, separate story.
