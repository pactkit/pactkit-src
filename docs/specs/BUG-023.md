# BUG-023: _rewrite_yaml drops unknown user-defined config keys

| Field     | Value |
|-----------|-------|
| Status    | Closed |
| Author    | System Architect |
| Release   | 1.3.1 |

## Context

`_rewrite_yaml()` in `config.py` reconstructs the entire YAML file from scratch, only writing keys it knows about:

```python
# Known keys written explicitly:
# version, stack, root, agents, commands, skills, rules, exclude,
# ci, issue_tracker, hooks, lint_blocking, auto_fix, venv,
# agent_models, rule_scopes
```

If a user has custom keys in their `pactkit.yaml` (e.g., `team`, `env`, `custom_paths`), these are silently deleted when `auto_merge_config_file()` triggers a rewrite.

### Trigger Conditions

`_rewrite_yaml` is called by `auto_merge_config_file()`, which runs on every `pactkit init` / `pactkit update`. So any user who upgrades PactKit and has custom keys will lose them on the next run.

### Impact

This is a data loss bug. While PactKit does not officially define user-extensible config keys, YAML files are commonly extended by users for their own tooling. Silently deleting unknown keys violates the principle of least surprise.

## Target Call Chain

```
deployer.py:_deploy_classic()
  → config.py:auto_merge_config_file(project_yaml)
    → user_data = yaml.safe_load(raw)         # has custom keys
    → added = [...]                            # some new sections backfilled
    → if added:
        → _rewrite_yaml(path, user_data)       # BUG: only writes known keys
        → path.write_text(...)                 # custom keys silently dropped
```

## Requirements

### R1: Preserve Unknown Keys
- `_rewrite_yaml()` MUST preserve any top-level keys in the data dict that are not part of the known schema.
- Unknown keys MUST be written to a clearly marked section at the end of the file.

### R2: Round-Trip Safety
- IF `_rewrite_yaml(path, data)` is called with data loaded from the same file, the output MUST contain all keys that were in the input (no silent data loss).
- The values of known keys MAY be reformatted (normalized), but unknown keys MUST preserve their original values.

### R3: Comment Marker for Unknown Keys
- Unknown keys SHOULD be written under a `# Custom — user-defined keys (preserved by PactKit)` comment.
- This makes it clear which section is PactKit-managed vs. user-defined.

### R4: Backward Compatibility
- Files without unknown keys MUST produce identical output to the current implementation.
- The known key ordering and formatting MUST remain unchanged.

## Acceptance Criteria

### AC1: Custom Key Preserved After Rewrite
- **Given** `pactkit.yaml` contains `team: backend` (unknown key)
- **And** a new PactKit version adds a new skill to the registry
- **When** `auto_merge_config_file()` runs and triggers `_rewrite_yaml()`
- **Then** the rewritten file still contains `team: backend`

### AC2: Nested Custom Key Preserved
- **Given** `pactkit.yaml` contains `deploy: {target: staging, region: us-east-1}` (unknown nested key)
- **When** `_rewrite_yaml()` is called
- **Then** the rewritten file contains the `deploy` section with both sub-keys intact

### AC3: Custom Keys in Separate Section
- **Given** `pactkit.yaml` contains custom keys `team` and `env`
- **When** `_rewrite_yaml()` is called
- **Then** the custom keys appear under a `# Custom` comment section
- **And** known PactKit keys appear in their standard sections above

### AC4: No Custom Keys — Output Unchanged
- **Given** `pactkit.yaml` contains only standard PactKit keys
- **When** `_rewrite_yaml()` is called
- **Then** the output is identical to the current implementation (no extra comment section)

### AC5: Known Key Values Still Normalized
- **Given** `pactkit.yaml` contains `lint_blocking: True` (capital T)
- **And** a custom key `team: backend`
- **When** `_rewrite_yaml()` is called
- **Then** `lint_blocking` is normalized to `lint_blocking: true` (lowercase)
- **And** `team: backend` is preserved as-is
