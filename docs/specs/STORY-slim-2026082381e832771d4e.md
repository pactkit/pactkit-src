## Background

STORY-slim-146/147 已将 `$project-act` 与 `$project-plan` 的长流程进度持久化为可验证 checkpoint，并能在新会话中检测 artifact drift 后返回下一安全步骤。然而真实 Codex 会话再次证明：可恢复状态并不等于持续执行。模型可以在某次工具调用成功后，仍有 HLD、Board 或后续 checkpoint 未完成时发送 final response；一旦 turn 结束，PactKit CLI 没有后台执行权，也不能自行唤醒 Codex。

现有 `ContinuationEngine` 只提供 `start`、`bind`、`checkpoint`、`status` 与只读 `resume`。它能拒绝伪造的 `completed`，却没有“当前 workflow 是否允许结束本 turn”的机器可读判定；`project-*` Skill 也没有统一要求在 final 前执行终止门禁。另一方面，Spec scaffold、Story 写入等关键操作仍可在没有 active run 的情况下直接执行，因此模型漏掉 workflow 指令后，系统甚至无法可靠发现一次未纳管的长流程。

本 Story 将补齐执行生命周期的最后一段：定义统一的 finish guard、关键写入的 active-run ownership、Codex 宿主可消费的 continuation protocol 与 agent-loop 验收。设计必须诚实区分“当前 turn 内由 Skill 约束继续执行”和“turn 已结束后由宿主重新调度”；没有宿主回调能力时不得宣称 PactKit 能自动唤醒模型。

## Requirements

### R1: 为持久化 Workflow 提供统一终止判定 (MUST)

Core MUST 为所有 `persistence=full` 的 workflow 提供统一、只读、机器可判定的 finish guard。输入为 run ID 或已绑定 Story ID，输出至少包含 `decision`、`workflow_id`、`run_id`、可选 `story_id`、当前 `step_id`、`next_step`、`status`、`reasons` 与进程 exit code。

仅以下状态允许调用方结束当前 turn：

- workflow 已通过其完成 validator 并持久化为 `completed`；
- workflow 已持久化为 `blocked`，blocker 非空，并明确标识需要用户输入、授权或外部状态变化。

`in_progress`、缺失 run、损坏状态、artifact drift、未验证的 blocker 或只包含进度说明的状态 MUST 返回非零，并给出下一安全步骤。finish guard MUST NOT 修改 checkpoint、刷新 fingerprints、重放写操作或把 `in_progress` 隐式转换为 `blocked/completed`。

### R2: 所有长流程 Skill 必须执行 Pre-Final Protocol (MUST)

全部 canonical `project-*` Skill MUST 声明统一 Managed Workflow 与 Pre-Final Protocol：命令开始时创建或恢复 run，在阶段边界写入 checkpoint；进度说明只能通过中间更新输出；在发送任何 final response 前必须调用 finish guard。若 guard 返回 continue/non-zero，agent MUST 在同一 turn 继续工具调用并执行 `next_step`，不得把“仍有剩余工作”包装成最终交付。若 guard 返回合法 blocked，final 必须包含 run ID、已验证边界、具体 blocker 和唯一的外部下一动作。

该协议 MUST 由共享模板/操作契约渲染到 Classic、OpenCode、Codex 与 Copilot，不得由 adapter 使用有损文本替换。部署 parity 测试必须验证 guard 命令、continue 分支、blocked 分支和“progress is not final”语义均保留。

### R3: 关键创建与治理写入必须验证 Active Run Ownership (MUST)

当调用来自纳入 `persistence=full` 的任一 `project-*` workflow 时，Spec scaffold、Story fact 创建/状态变更及其他 registry 声明的关键写操作 MUST 能接收 run identity，并在写入前验证：run 存在、workflow 匹配、当前 step 允许该操作、Story 绑定一致且 checkpoint 未 completed。校验失败 MUST 在写入前停止。

为保持现有 standalone skill 与旧 CLI 兼容，直接调用不得被无条件破坏；但必须显式选择 standalone/manual 模式，且机器可读输出标记 `managed=false`。由 `project-plan`/`project-act` 模板发起的关键写入 MUST 使用 managed 模式。不得依赖环境变量中的未验证 run ID，也不得让用户输入直接参与状态文件路径。

### R4: 定义宿主级自动续跑协议并诚实声明能力边界 (MUST)

Core MUST 提供稳定的机器接口，使 Codex CLI wrapper、CI runner 或未来宿主 hook 可以查询未完成 run，并获得结构化动作：`continue_current_turn`、`resume_session`、`await_user` 或 `done`。接口必须携带幂等 resume token/运行身份，不得直接执行模型调用，也不得把通用 Core 耦合到某一家模型 SDK。

当宿主支持 turn completion hook 或外层 agent loop 时，参考 runner MUST 在模型尝试结束后调用 finish guard；若仍为 `in_progress`，以有界重试恢复同一 session/run。达到最大连续恢复次数、发现无进展、重复相同步骤、权限拒绝或 artifact drift 时 MUST fail closed 为 blocked，并向用户交付可恢复信息，防止无限循环和重复副作用。

当宿主不提供回调/重入能力时，PactKit MUST 明确报告 `auto_resume_available=false`，只承诺 checkpoint 可恢复和 Pre-Final 软约束，不得宣称“自动续跑”或“绝不停止”。

### R5: 防止无进展循环、并发恢复与副作用重放 (MUST)

每次宿主续跑尝试 MUST 记录 attempt、上次 step/evidence digest、session locator、时间戳和 termination reason。相同 step 与 evidence digest 连续出现、run 已被其他 owner lease、blocked/completed、或超过可配置上限时必须拒绝再次调度。owner lease 必须有明确过期语义并使用现有 run lock/atomic write 原语，进程崩溃后可安全接管。

自动续跑不得跨越 registry 中的 `manual_operations`，不得自动执行 publish、tag、push、PR、release、archive 或未经确认的用户所有写入。恢复只允许从 validator 返回的下一安全步骤继续，create-only 操作必须 verify-before-write。

### R6: 提供真实 Agent-Loop 验收而非只测状态存储 (MUST)

测试必须模拟“工具返回成功后模型试图 final，但 workflow 尚未完成”的完整事件序列，并验证 harness 拒绝终止或生成下一次 resume 调度。至少覆盖 Plan 在 Spec lint 后尚未同步 HLD/Board、Act 在 GREEN 后尚未 regression、合法 blocked、completed、无进展循环、并发 owner、宿主不支持自动续跑和高副作用边界。

CLI 状态机单测、prompt 字符串包含测试和 manifest hash 只能作为下层证据，不能替代 agent-loop 验收。每个内置格式 MUST 运行契约测试；Codex 还必须有真实 adapter 渲染与 runner handshake 测试。

### R7: 诊断、可观测性与迁移必须明确呈现保证等级 (SHOULD)

`pactkit doctor` SHOULD 报告 active workflow 无 finish-guard 支持、宿主 auto-resume capability、孤儿/陈旧 lease、反复无进展以及模板缺少 Pre-Final Protocol。`pactkit workflow status|finish-guard` SHOULD 支持 JSON，日志 SHOULD 使用 run ID、workflow、step、attempt 和 reason code，且不得记录 prompt 全文、凭证或敏感 evidence。

STORY-slim-147 的 schema v2 状态 MUST 可直接读取；新增字段应有安全默认值。现有 completed/blocked run 不得因升级被重新激活。

### R8: 所有 Project 命令必须纳入统一生命周期 (MUST)

`project-plan`、`project-act`、`project-check`、`project-done`、`project-init`、`project-sprint`、`project-hotfix`、`project-design`、`project-clarify`、`project-release`、`project-pr` 与 `project-debug` MUST 全部在可靠性注册表中声明为 `persistence=full`，并拥有至少一个开始边界和一个可验证完成边界。共享协议 MUST 注入每个 canonical 模板，包括从 `prompts/workflows.py` 注册的命令。

每个命令的最终边界 MUST 声明并验证与其职责对应的结构化 evidence，不能接受通用 `completion=verified` 自我声明。缺少团队编排 API 的平台仍 MUST 部署 `project-sprint` 入口，并在同一受管 run 中串行执行 Plan → Act → Check → Close。

高副作用命令的 workflow 持久化不得等同于预授权：commit、archive、tag、publish、release、push 与 pull request MUST 继续经过 manual operation boundary。缺少 run、未到最终边界、完成证据无效或提前 final 时 MUST 由同一 finish guard 拒绝。

## Acceptance Criteria

### AC1: 未完成 Workflow 不允许正常结束 (R1, R2)

- **Given** `project-plan` run 停留在 `spec_linted`，HLD 或 Board 尚未同步
- **When** agent 在工具结果后准备发送 final 并调用 finish guard
- **Then** guard 以非零退出返回 `continue_current_turn` 和 `board_synced`/对应下一安全步骤，checkpoint 保持不变，Skill 契约要求继续工具调用

### AC2: 只有 Completed 或真实 Blocked 可结束 (R1)

- **Given** 分别存在 completed、带外部 blocker 的 blocked、空 blocker 与损坏状态
- **When** 对各 run 执行 finish guard
- **Then** 前两者分别返回 `done` 与 `await_user` 且 exit 0；后两者 fail closed，不能伪装为可终止状态

### AC3: Managed 写入拒绝缺失或错误 Run (R3)

- **Given** Plan 尝试 scaffold Spec 或创建 Story fact，但 run 缺失、workflow 不匹配、step 不允许或 Story 绑定冲突
- **When** 关键写操作以 managed 模式执行
- **Then** 在任何目标文件变化前失败；合法 run 只执行一次，重试时验证匹配产物而不覆盖或重复创建

### AC4: Standalone 调用保持兼容但明确未纳管 (R3)

- **Given** 用户独立调用 scaffold 或 board skill，且没有 active workflow
- **When** 显式选择 standalone/manual 模式
- **Then** 保持现有行为并输出 `managed=false`；从 project-plan 模板调用时未携带 run identity 则失败

### AC5: 支持 Hook 的宿主自动续跑同一 Run (R4, R5)

- **Given** 模拟 Codex 宿主捕获到模型 final，而 finish guard 返回 `continue_current_turn`
- **When** runner 在预算内重新进入同一 session 并携带 opaque resume token
- **Then** workflow 从 validator 指定的 next step 继续，attempt 单调增加，已完成 create-only/外部副作用不被重放

### AC6: 无宿主回调时不作虚假保证 (R4)

- **Given** 当前 adapter/宿主没有 turn completion hook 或 session re-entry 能力
- **When** 查询 runtime capability 或执行 finish guard
- **Then** 返回 `auto_resume_available=false`，仍提供 run ID 和手工 resume 指令，但文档、部署摘要和 doctor 不声称能够自动唤醒 Codex

### AC7: 无进展与并发续跑安全停止 (R5)

- **Given** 同一 step/evidence digest 连续多次、两个 runner 竞争 owner lease，或达到最大恢复次数
- **When** runner 尝试继续调度
- **Then** 仅一个 owner 可推进；无进展或超限被转换为带 reason code 的安全 blocked，不产生重复写入或无限循环

### AC8: 高副作用边界永不自动跨越 (R5)

- **Given** registry 将 publish、tag、push、PR、release 或 archive 声明为 manual operation
- **When** host runner 请求自动续跑
- **Then** finish decision 为 `await_user`，未获得新授权前不调用对应命令，历史确认不得跨 run 重用

### AC9: Agent-Loop 测试捕获工具后提前 Final (R6)

- **Given** 测试 agent 在写完第二个 Spec 并通过 lint 后返回“剩余 HLD/Board 未完成”的 final
- **When** conformance harness 评估输出与真实 workflow state
- **Then** 测试失败并证明 final 未被接受；当 agent 继续完成 HLD、Board 和 completion checkpoint 时同一测试通过

### AC10: 四平台部署保留终止协议且保证等级透明 (R2, R4, R6, R7)

- **Given** Classic、OpenCode、Codex、Copilot 的隔离部署结果
- **When** 运行结构化语义、manifest、adapter compatibility 和 runner capability 测试
- **Then** 所有格式保留 Pre-Final Protocol 与 finish guard；仅真实支持 re-entry 的宿主标记 auto-resume，Codex adapter 的声明与实测能力一致

### AC11: 所有 Project 命令拒绝阶段性 Final (R2, R8)

- **Given** 任一内置 `project-*` 命令刚完成前置或中间阶段，但尚未写入最终 completion checkpoint
- **When** agent 尝试发送 final 并执行统一 finish guard
- **Then** guard 返回 `continue_current_turn` 与下一边界；12 个 canonical 模板均包含 start/resume、checkpoint 和 pre-final 指令

### AC12: Done 与高副作用命令保持可恢复但不越权 (R5, R8)

- **Given** `project-done` 已完成审计但尚未归档/提交，或 Release/PR 即将执行人工副作用
- **When** agent 在工具结果后提前 final 或 host runner 尝试自动跨越操作边界
- **Then** Done 不能完成且可从下一边界恢复；commit/archive/tag/publish/release/push/PR 仍返回 `await_user`，只有执行并验证最终边界后才返回 `done`

## Target Call Chain

    any $project-* command
      -> pactkit workflow start|checkpoint <run>
      -> ContinuationEngine + workflow-specific validator
      -> managed scaffold / StoryRepository operation validates run ownership
      -> agent proposes final response
      -> pactkit workflow finish-guard <run> --json
          -> completed                         => done / exit 0
          -> legitimate blocked               => await_user / exit 0
          -> in_progress                       => continue_current_turn / non-zero
          -> corrupt, drift, invalid blocker   => fail_closed / non-zero
      -> HostContinuationProtocol
          -> hook/re-entry available           => bounded resume of same session/run
          -> hook/re-entry unavailable         => manual resume handoff, no false guarantee

    Host runner resume loop
      -> acquire run owner lease
      -> compare step + evidence digest + attempt budget
      -> resume same session with opaque run identity and next step
      -> verify progress via checkpoint
      -> release/renew lease or block on no progress

## Technical Design

### Lateral Scan Results

- Operation: workflow lifecycle and termination decision.
- Existing implementations: `ContinuationEngine` provides generic Plan/Act run state; legacy `ContinuationStore` remains the Act compatibility facade.
- Assessment: extend the shared engine and registry with finish decisions and managed-operation ownership. A third command-specific state store or adapter-local scheduler would duplicate locking, fingerprints and completion semantics and is therefore rejected.

### Archaeology and capability delta

Codegraph selected the configured provider with a fresh index. The current path is `cli.main()` → `ContinuationEngine.start/bind_story/checkpoint/resume()` → `PlanEvidenceValidator` or `ActEvidenceValidator` → atomic JSON state. `resume()` is intentionally read-only and returns a decision, but no caller intercepts an agent final response. Codex officially exposes Skills and resumable sessions/subagents, while a Skill itself cannot regain control after its turn has ended.

The existing engine and registry remain authoritative. This Story extends them with termination and ownership contracts; it MUST NOT create a second scheduler-specific state store. Host integration consumes a small protocol and stays outside workflow validation.

### Three guarantee levels

| Level | Mechanism | Guarantee | Limitation |
|-------|-----------|-----------|------------|
| Instruction | Pre-Final Protocol in Skill | Encourages same-turn continuation and correct commentary/final usage | Model may ignore prompt instructions |
| Process | `finish-guard` + managed write ownership | Deterministically detects incomplete/invalid termination and untracked writes | Cannot execute after an already-ended process without a caller |
| Host | completion hook / bounded runner | Can reject or re-enter an incomplete turn automatically | Requires platform integration and session resume capability |

Deployment and documentation MUST report the highest level actually available, rather than collapsing all three into “resumable” or “never stops”.

### Finish decision model

Use a closed enum with stable reason codes. `finish-guard` derives its result from persisted state plus validator fingerprints and runtime capability; it never trusts an agent-provided completion claim. Exit 0 means the caller may yield to the user (`done` or legitimate `await_user`), while every other decision is non-zero. JSON is the canonical machine interface; human text is a projection.

### Managed operation ownership

Registry definitions gain allowed managed operations per step. CLI entry points accept an explicit run ID/token and call a shared guard before mutation. Tokens are opaque identifiers, not bearer secrets or filesystem paths. Standalone mode remains available for direct skill use but must be explicit and observable. This avoids breaking reusable atomic skills while preventing project workflows from silently bypassing lifecycle tracking.

### Host continuation protocol

Core exports decisions and state only. A host adapter may implement a hook or wrapper that maps `continue_current_turn` to the platform's supported continuation primitive. It must preserve the same run, validate progress after every attempt and enforce an owner lease plus bounded retry budget. No generic PactKit module imports Codex/Claude/OpenCode SDKs.

### Failure and security model

Malformed state, path traversal, unknown workflow, stale fingerprints, unsupported host capabilities and lease ambiguity fail closed without mutating trusted evidence. Logs redact evidence using existing sanitization. A legitimate blocker must identify an external dependency; “ran out of context”, “tool returned”, “more work remains” and self-authored progress summaries are not valid blockers. Manual operations always require fresh authorization.
