## Background

PactKit 当前把一条完整 PDCA 命令同时实现为长 Prompt、持久化 continuation 状态和宿主结束门禁。该形态与 Claude Code/OpenCode 的连续命令体验较契合，却把 Codex/Copilot 不同的 turn、thread、审批与恢复生命周期误当成可由同一 Prompt 兼容的细节。真实 Codex 会话已连续出现模型在明确列出剩余工作后结束 turn；随后新增的 Stop hook 又因宿主 JSON 契约不匹配而失败。继续强化“不要提前结束”的提示或复制一套 Codex 专用业务流程，只会增加双重事实源和版本漂移。

对 `obra/superpowers` 的源码分析表明，其跨产品能力来自一套无持久状态的共享方法论 Skills 与多个薄安装外壳，而不是跨宿主的强制长流程编排。PactKit 应采用同样的 portable methods 边界，同时保留自己独有的可验证治理能力：Core 成为 workflow truth，将长命令拆成短小、可租约、可重试的 Work Unit；宿主 adapter 只负责发现 Skills、执行 Work Unit 和回传 Attempt/Receipt。首期以 `project-plan` 验证该架构，Stop hook 降级为 advisory，Board/context/checkpoint 收口为 Core 原子 finalize。

## Requirements

### R1: 建立三层产品边界与单一事实源 (MUST)

PactKit MUST 明确定义并在代码依赖上隔离三层：`Portable Methods` 保存跨宿主的方法论 Skills；`Core Workflow Engine` 保存 workflow definition、状态转换、evidence validator、治理事实与 finalize；`Host Adapter` 只处理宿主发现、任务投递、事件翻译和 capability probe。Methods 和 adapter 不得复制 workflow steps、Spec/Story schema、完成规则或 Board/context 写入逻辑。

Agent 的自然语言回复和宿主 turn completion MUST 仅表示一次 `ExecutionAttempt` 结束，不得直接推进或完成 `WorkflowRun`。只有 Core 验证仓库证据后才可改变权威状态。

### R2: 将长命令编译为有界 Work Unit (MUST)

Core MUST 将 workflow 当前步骤投影为版本化 `WorkUnit`，至少包含 `run_id`、`unit_id`、`workflow_id`、目标、输入引用/摘要、允许读写范围、禁止操作、验收命令、人工授权要求、超时/租约和 `Receipt` schema version。单个 Work Unit SHOULD 限于一个明确目标和可独立验证的少量文件；宿主不得自行选择下一步骤。

Work Unit 必须支持 acquire、renew、submit、reject、expire 和 retry。重复 acquire/submit 使用 idempotency key；过期或非 owner attempt 不得写入可信 evidence。Create-only 与外部副作用必须在重试前由 Core 验证。

### R3: 建立 Attempt 与 Evidence Receipt 协议 (MUST)

每次宿主执行 MUST 记录独立 `ExecutionAttempt`，至少包含 host、session/thread/turn 的不可逆引用、unit/version、起止状态、capabilities、结果引用和失败原因。Adapter 提交的 `EvidenceReceipt` 只是候选证据；Core 必须重新读取文件、运行确定性 validator 并计算指纹，不能信任 `success=true` 或自然语言“已完成”。

Attempt 终态至少区分 `succeeded`、`rejected`、`interrupted`、`host_error`、`malformed_result` 和 `awaiting_approval`。Attempt terminal 不等于 Workflow terminal；若仍有 ready unit，Core 必须返回下一执行决策。

### R4: Host Capability Contract 与诚实降级 (MUST)

Core MUST 定义版本化 Host Capability Contract，覆盖 instructions/skills discovery、structured result、tool execution、approval、lifecycle events、thread resume、turn steer、background execution 和 cancellation。Adapter 启动时报告实际能力与验证来源；Core 根据 workflow 最低能力选择 `portable`、`guided`、`resumable` 或 `managed` 执行模式。

缺少 thread resume/lifecycle API 的宿主 MUST 降级为生成下一 Work Unit 的 manual-resume 模式，不得宣称自动完成。Claude/OpenCode 可保留原生命令 facade；Codex managed runtime 应使用官方 App Server/SDK 的 thread/turn 生命周期；Copilot 依据实际 IDE capability 选择 managed bridge 或 manual resume。

### R5: Portable Methods 采用单一内容源和薄宿主包装 (MUST)

现有长 command 中可跨产品的方法论 MUST 提取为小粒度 Skills，例如 requirement clarification、architecture trace、Spec writing、TDD、verification 和 release preparation。Canonical Skill 内容只存在一份；Claude、OpenCode、Codex、Copilot 的 manifest/目录/metadata 转换为薄包装，并通过同步与发现测试验证。

Methods 只描述局部推理和操作方法，不维护 WorkflowRun，不写 completion checkpoint，不要求模型“持续到所有阶段完成”。宿主不支持的工具必须通过 capability 声明和显式降级处理，而不是在 Prompt 内伪装等价能力。

### R6: project-plan 首期迁移与原子 finalize (MUST)

首期 MUST 将 `project-plan` 迁移为 Work Unit 驱动流程，至少覆盖 preflight、clarification、archaeology、story identity、Spec scaffold/content/security/lint 和 finalize。旧命令入口保持兼容，但每次只领取当前 unit，并由 Core 决定下一步。

`finalize-plan` MUST 在同一 Story/run 锁和可恢复 journal 下验证 Spec/HLD、upsert Story fact、重建 Board、刷新 context、写入 fingerprints 并完成 run。任一步失败不得留下“workflow completed 但 projection 未同步”的状态；Board/context 始终是 Story facts 可重建的投影。

### R7: Stop Hook 退出正确性路径 (MUST)

Codex Stop hook MUST NOT 作为 workflow correctness 或自动续跑的必要条件。默认部署不得安装强制续跑 Stop hook；若未来保留 advisory hook，它只能提示 active run，并必须经过宿主版本 schema、stdout purity 和真实 host smoke test。Hook 缺失、未信任或失败不得影响 Core 的可恢复性。

原 `HostContinuationRunner` 应收敛为兼容 facade 或删除，其职责由 Work Unit scheduler 和 host adapter 接管。不得通过更强 Prompt、无限 block 或 transcript 文本推断补偿宿主能力缺失。

### R8: 兼容迁移、可观测性与发布边界 (MUST)

现有 schema v1/v2 continuation、已完成 Story facts 和命令入口 MUST 可读取；迁移采用 expand → shadow → Plan cutover → 其他 workflow cutover → legacy removal。迁移期间旧/新引擎不得同时写同一 run，且 rollback 必须保留原始状态。

系统 MUST 记录不含 prompt/凭证的 run/unit/attempt/decision/reason/latency/adapter version，并提供 doctor 输出实际 guarantee level。Core 与 adapter 独立发布时必须协商 protocol version；不兼容组合 fail closed，不得回退到长 Prompt 假完成。

## Acceptance Criteria

### AC1: Agent final 不再等于 workflow 完成 (R1, R3)

- **Given** Codex 在 Plan 的 Spec lint unit 后输出 final，且 Board/finalize 尚未完成
- **When** adapter 记录 turn terminal 并提交 Attempt
- **Then** Core 只验证并完成当前 unit，WorkflowRun 保持 running 且返回 finalize unit，不依赖 Stop hook

### AC2: Work Unit 有界且不可越权推进 (R2)

- **Given** 当前 unit 仅允许修改一个 Spec 并运行 spec-lint
- **When** adapter 尝试提交下一阶段 evidence、写入 Board 或使用错误 owner/过期 lease
- **Then** Core 拒绝 receipt 和状态推进，保留可信基线并返回稳定 reason code

### AC3: Receipt 必须由真实证据复验 (R3)

- **Given** agent 声称成功但 Spec 含 placeholder、lint warning 或文件指纹不匹配
- **When** Core 验证 EvidenceReceipt
- **Then** Attempt 标记 rejected，unit 进入可诊断 retry，WorkflowRun 不前进

### AC4: 宿主能力决定模式而非业务语义 (R4)

- **Given** Claude/OpenCode、Codex App Server 和不支持 resume 的 Copilot capability manifests
- **When** 同一 Plan workflow 请求下一动作
- **Then** 三者获得语义相同的 Work Unit，执行模式分别可为 native facade、managed turn 和 manual resume，完成 validator 完全相同

### AC5: Portable Methods 单源同步 (R1, R5)

- **Given** canonical Spec-writing Skill 更新
- **When** 构建四种宿主包并运行 discovery/parity 测试
- **Then** 每个宿主可发现同一 method version，平台包只含 manifest/metadata/路径适配，且不存在复制的 workflow completion logic

### AC6: Plan finalize 崩溃可恢复且投影一致 (R6)

- **Given** Spec/HLD 已验证且 finalize 在 Story fact 写入后、Board/context 替换前中断
- **When** 使用同一 idempotency key 重试 finalize
- **Then** Core 根据 journal roll forward，Story fact、Board、context 和 completed checkpoint 最终一致且无重复 Story

### AC7: 无 Stop hook 仍可恢复 (R7)

- **Given** Codex 未安装任何 PactKit Stop hook，某个 turn 在 unit 完成前结束
- **When** runtime 或用户调用 resume/status
- **Then** Core 从 WorkflowRun/WorkUnit/Attempt 返回准确下一步，且不会因 hook 缺失丢失或伪造完成状态

### AC8: Legacy 状态无损迁移 (R8)

- **Given** schema v1/v2 的 in-progress、blocked 和 completed fixtures
- **When** 新引擎读取、迁移、失败回滚及重新打开
- **Then** 原状态和证据可追溯，completed 不回退，失败不覆盖源文件，单 run 只有一个 writer

### AC9: 保证等级由真实宿主 E2E 支撑 (R4, R8)

- **Given** adapter 仅通过模板/单元测试但没有真实 thread/turn E2E
- **When** doctor 或 manifest 查询 guarantee level
- **Then** 最多报告 portable/guided；只有真实宿主验证 acquire→execute→submit→next/finalize 后才可报告 resumable/managed

## Target Call Chain

User invokes project command
  → Core WorkflowEngine.start/resume
  → WorkUnitScheduler.acquire(host capabilities)
  → HostAdapter.execute(work unit)
      ├─ Claude/OpenCode native facade
      ├─ Codex App Server thread/resume + turn/start
      └─ Copilot managed bridge or manual package
  → ExecutionAttempt + EvidenceReceipt
  → Core validator rereads repository evidence
      ├─ reject/retry/await approval
      ├─ accept → next WorkUnit
      └─ finalize-plan → journaled Story/Board/context/run commit

## Out of Scope

- 在本 Story 中一次性迁移 Act/Check/Done/Release/Sprint 的全部步骤；它们在 Plan 验证后分批迁移。
- 复制完整 `pactkit-for-codex` 或在 adapter 中维护第二套 workflow/schema/validator。

- 云端队列、跨机器调度、多租户服务或新的模型供应商抽象。
