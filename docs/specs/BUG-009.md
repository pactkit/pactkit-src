# BUG-009: pactkit update does not backfill project-level .claude/pactkit.yaml

| Field     | Value |
|-----------|-------|
| Status    | Open |
| Author    | System Architect |
| Release   | 1.2.0 |

## Context

PactKit has a **dual-config architecture**:

1. **Global config** (`~/.claude/pactkit.yaml`) — Full config with component lists (agents, commands, skills, rules) and feature flags (ci, hooks, lint_blocking, auto_fix, issue_tracker). Used by the Python deployer to decide what to deploy.
2. **Project-level config** (`$PROJECT/.claude/pactkit.yaml`) — Minimal config (stack, version, root) created by `/project-init` prompt template. Read by AI agents during PDCA commands.

When `pactkit update` runs, it calls `_deploy_classic()` which:
- Resolves target to `~/.claude/` (global)
- Calls `auto_merge_config_file()` on the **global** config only
- Calls `_generate_config_if_missing()` on the **global** config only

The **project-level config** at `$CWD/.claude/pactkit.yaml` is never touched by `pactkit update`. This means:

1. Feature flags (hooks, ci, lint_blocking, auto_fix, issue_tracker) are never backfilled into the project config
2. STORY-034's Plan Phase 0.5 Config Completeness Check detects missing sections in the project config, runs `pactkit update`, but `pactkit update` only fixes the global config — the project config remains stale
3. AI agents reading the project-level config never see the new feature flags

### Related Impact

- **Hooks**: Users who enabled hooks globally still don't see them per-project because the project config has no `hooks` section
- **CI/CD**: Same issue — `ci.provider` in global config is invisible to the project
- **Lint settings**: `lint_blocking` and `auto_fix` in global config are invisible to the project

## Target Call Chain

```
pactkit update
  → deploy() → _deploy_classic()
    → auto_merge_config_file(~/.claude/pactkit.yaml)     ← global only (BUG)
    → _generate_config_if_missing(~/.claude/)             ← global only (BUG)
    → (missing) auto_merge_config_file($CWD/.claude/pactkit.yaml)  ← NEW
```

## Requirements

1. `_deploy_classic()` MUST also call `auto_merge_config_file()` on the project-level config at `$CWD/.claude/pactkit.yaml` if it exists
2. The project-level backfill MUST NOT create a project config if it doesn't exist (that's `/project-init`'s job)
3. The project-level backfill MUST NOT overwrite existing user values — only add missing sections
4. The backfill SHOULD report what was added to the project config separately from the global config
5. `_generate_config_if_missing()` MUST NOT be called for the project-level path (project config is optional, created by `/project-init`)

## Acceptance Criteria

### AC1: Project-level config backfilled on pactkit update
- **Given** a project with `$CWD/.claude/pactkit.yaml` containing only `stack`, `version`, `root`
- **When** `pactkit update` is run from the project directory
- **Then** `$CWD/.claude/pactkit.yaml` is backfilled with missing sections (hooks, ci, issue_tracker, lint_blocking, auto_fix)

### AC2: Global config still backfilled
- **Given** the existing global config at `~/.claude/pactkit.yaml`
- **When** `pactkit update` is run
- **Then** the global config is still auto-merged as before (no regression)

### AC3: Non-existent project config not created
- **Given** a directory with no `.claude/pactkit.yaml`
- **When** `pactkit update` is run from that directory
- **Then** no project-level config is created

### AC4: Existing values preserved
- **Given** a project config with `ci: {provider: github}`
- **When** `pactkit update` runs the backfill
- **Then** `ci.provider` remains `github` (not overwritten with default `none`)

### AC5: Output distinguishes global vs project config
- **Given** both global and project configs need backfilling
- **When** `pactkit update` runs
- **Then** output shows which config was updated (e.g., "Project config refreshed: added hooks, ci sections")
