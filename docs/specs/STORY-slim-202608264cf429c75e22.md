## Background

Full-codebase review (2026-08-26) found that the deployment subsystem's
safety model — "manifest-hash ownership proof: a deployed file may only be
overwritten or deleted when the deployment manifest (.pactkit-deployed.json)
records its sha256 and the on-disk bytes still match; otherwise a
`.pactkit-new` candidate is
written alongside" — is enforced only for **rules** (`_deploy_rules`) and
**guides** (`_deploy_guides`). Five gaps leave the largest deployed
surfaces unprotected, reproducing the failure class of the two historical
codex `config.toml` wipe incidents:

1. `_deploy_skills` (deployer.py:662-676) unconditionally
   `atomic_write`s SKILL.md and registered scripts — no manifest lookup,
   no drift detection, no `.pactkit-new` candidate. Any user customization
   of a deployed skill is destroyed on every `pactkit update`.
2. `_deploy_agents` (deployer.py:1045-1050) deletes agent files **by
   filename alone** (`f.name in managed_agent_files and f.stem not in
   enabled_set → unlink()`), violating the codebase's own invariant
   ("never infer ownership from its name alone", deployer.py:797). A
   user-authored `system-architect.md` is destroyed when that agent is
   disabled. Enabled agents are likewise overwritten unconditionally.
3. `pactkit_owned_files` (deploy_manifest.py:92-102) records every file
   under a skill directory via `rglob("*")` as pactkit-owned — a user file
   dropped inside `skills/pactkit-act/references/` gets false ownership
   recorded, authorizing future overwrite. The guides section of the same
   function (:139) states the correct principle but applies it only to
   guides.
4. `_deploy_claude_md` (deployer.py:995-1011) overwrites an **unreadable**
   CLAUDE.md with the 2-line template — destroying the file precisely when
   ownership cannot be verified — and replaces the **entire** file when the
   first line matches the managed header, losing any user content appended
   below it.
5. `rollback_paths` (deployment_transaction.py:62) guards with
   `except Exception`, which does not catch `KeyboardInterrupt` /
   `SystemExit` — a Ctrl-C mid-deployment (the most common interactive
   abort) performs no rollback; the backup TemporaryDirectory is silently
   deleted and partial writes persist. The adapters (pactkit-codex,
   pactkit-copilot) wrap writes that include `config.toml` with this
   boundary.

Lateral scan: the ownership-check pattern already exists as two
near-identical copies (`_deploy_rules` deployer.py:797-905,
`_deploy_guides` deployer.py:923-964) and the `.pactkit-new`
conflict-marker logic is repeated in 8 places. Adding skills/agents as a
third and fourth copy crosses the ≥3 threshold — this Spec mandates a
shared abstraction instead.

## Requirements

### R1: Shared ownership abstraction (MUST)

The manifest-read + preserve-or-write logic MUST be extracted into a single
shared helper in `deploy_manifest.py` (e.g. `load_previous_hashes(deploy_root)`
and `preserve_or_write(path, content, previous_hashes, label)` implementing
the existing `_deploy_rules` semantics: overwrite only when the destination
is absent, byte-identical, or manifest-proven unchanged; otherwise write the
`.pactkit-new` candidate and print a preservation warning). `_deploy_rules`
and `_deploy_guides` MUST be refactored to route through it, and skills and
agents (R2, R3) MUST use it rather than adding new copies — a corrupted
manifest advisory still MUST NOT make deployment destructive (existing
fail-safe semantics preserved).

### R2: Skill deployment ownership proof (MUST)

`_deploy_skills` MUST verify ownership before writing SKILL.md or a
registered script file. When the destination exists and its bytes are neither
identical to the newly rendered content nor matching the manifest-recorded
hash, the deployed file MUST be preserved untouched and the new content
MUST be written to a `.pactkit-new` sibling with a warning — identical to
rule drift handling. Unmodified or manifest-proven files are updated in
place. This requirement covers every artifact deployed under
`skills/`, including command skills written by `_deploy_commands`
(QA clarification 2026-08-26: commands deploy as skills since
STORY-slim-063 and are recorded by the same manifest).

### R3: Agent file deletion and overwrite by ownership proof (MUST)

`_deploy_agents` MUST NOT delete an agent `.md` file by filename alone.
Retirement of a disabled agent MUST require the previous manifest to record
the file's hash AND the current bytes to match. A same-named file without
manifest proof is user-owned and MUST be preserved. Overwriting an enabled
agent file MUST use the same preserve-or-write semantics as R2.

### R4: Manifest MUST NOT over-claim skill directory ownership (MUST)

`pactkit_owned_files` skill section MUST record only registered artifacts
(the skill's SKILL.md and its registered script filenames from the skill
manifest), not `rglob("*")` enumeration. Additional files inside a skill
directory MUST NOT appear in the manifest `files` map unless their bytes
match rendered PactKit content.

### R5: CLAUDE.md preservation on unverifiable ownership (MUST)

When the existing global CLAUDE.md cannot be read (OSError,
UnicodeDecodeError), `_deploy_claude_md` MUST NOT overwrite it — the
original MUST be preserved untouched and the new template written as a
`.pactkit-new` candidate. When the file is PactKit-managed (managed header)
but contains user content after the managed block, update MUST replace only
the managed block and preserve the trailing user content. When the managed
block boundary cannot be recognized — non-blank user content between the
managed header and the runtime import line, or the import line appearing
only inside user content — the file MUST be preserved untouched with a
candidate (QA clarification 2026-08-26).

### R6: Rollback covers interrupting exits (MUST)

`rollback_paths` MUST catch `BaseException` (not just `Exception`) so
KeyboardInterrupt and SystemExit trigger the same snapshot-restore path.
Re-raising MUST preserve the original exception.

### R7: Rollback restore isolation (SHOULD)

Each restore step in `rollback_paths` SHOULD be individually guarded so a
failure restoring one path does not abort restoration of the remaining
snapshots; the original deployment exception SHOULD still be re-raised.

### R8: Retire disabled skills by manifest proof (SHOULD)

A skill disabled in config whose deployed directory is manifest-proven
unmodified SHOULD be retired on update (removed from disk and from the new
manifest), mirroring rule retirement. A drifted skill directory MUST be
preserved with a warning.

## Acceptance Criteria

### AC1: User-modified skill preserved (R2)

- **Given** a deployed skill `skills/pactkit-act/SKILL.md` whose bytes drift
  from both the rendered new content and the manifest-recorded hash
- **When** `pactkit update` runs
- **Then** the drifted SKILL.md is byte-identical to before, a
  `SKILL.md.pactkit-new` candidate exists, and a preservation warning is
  printed

### AC2: Unmodified skill updates in place (R2)

- **Given** a deployed skill whose bytes equal the manifest-recorded hash
- **When** `pactkit update` runs with new rendered content
- **Then** SKILL.md is overwritten in place and no `.pactkit-new` file is
  created

### AC3: Agent deletion requires proof (R3)

- **Given** `agents/system-architect.md` exists on disk and the agent is
  disabled in config
- **When** `pactkit update` runs
- **Then** the file is deleted if and only if the previous manifest records
  its hash and the bytes match; otherwise it is preserved with a warning

### AC4: User file in skill dir not claimed (R4)

- **Given** `skills/pactkit-act/references/my-notes.md` (user-created,
  not in the skill manifest)
- **When** `write_deploy_manifest` runs
- **Then** `my-notes.md` does not appear in the manifest `files` map

### AC5: Unreadable CLAUDE.md preserved (R5)

- **Given** a global CLAUDE.md that raises OSError or UnicodeDecodeError on
  read
- **When** `_deploy_claude_md` runs
- **Then** the original file is untouched on disk and a
  `CLAUDE.md.pactkit-new` candidate is written

### AC6: Appended CLAUDE.md content survives managed update (R5)

- **Given** a global CLAUDE.md whose first line is the PactKit managed
  header and whose body contains additional user lines below the managed
  block
- **When** `pactkit update` runs
- **Then** the managed block is refreshed and every non-managed line is
  preserved verbatim

### AC7: Ctrl-C mid-deployment rolls back (R6)

- **Given** an adapter deployment wrapped in `rollback_paths` with existing
  files snapshotted
- **When** the deployment body raises KeyboardInterrupt
- **Then** all snapshotted paths are restored to their pre-deployment bytes
  and the KeyboardInterrupt propagates

### AC8: Disabled skill retired with proof (R8)

- **Given** a skill disabled in config whose deployed directory bytes match
  the previous manifest
- **When** `pactkit update` runs
- **Then** the skill directory is removed and absent from the new manifest;
  a drifted directory is preserved with a warning

### AC9: Shared helper is the single ownership path (R1)

- **Given** rules, guides, skills, and agents each with a drifted
  deployed file
- **When** `pactkit update` runs
- **Then** all four artifact types exhibit identical preservation semantics
  (original preserved, `.pactkit-new` candidate written, warning printed),
  and the manifest-read + preserve-or-write logic exists in exactly one
  implementation in `deploy_manifest.py`

### AC10: Rollback completes despite a restore failure (R7)

- **Given** an adapter deployment wrapped in `rollback_paths` with two
  snapshotted paths, where restoring the first raises OSError
- **When** the deployment body raises
- **Then** the second path is still restored to its pre-deployment bytes
  and the original deployment exception is re-raised

## Target Call Chain

```
cli.py (init/update)
  → generators/deployer.py: _deploy_classic
      → _deploy_skills          [R2: preserve-or-write per artifact]
      → _deploy_agents          [R3: proof-based retire/overwrite]
      → _deploy_claude_md       [R5: unreadable/appended-content safety]
      → _deploy_rules           [R1: refactor to shared helper]
      → _deploy_guides          [R1: refactor to shared helper]
      → deploy_manifest.write_deploy_manifest
          → pactkit_owned_files [R4: registered artifacts only]
  adapters (pactkit-codex / pactkit-copilot deployer)
    → deployment_transaction.rollback_paths  [R6/R7: BaseException + isolation]
```

Shared ownership helper lands in `deploy_manifest.py` (single source of
truth for manifest semantics), consumed by `generators/deployer.py`.

## Security Scope

| Check | Applicable | Reason |
|-------|------------|--------|
| SEC-1 | Yes | Source code changes to deployment write paths |
| SEC-2 | Yes | Reads user-controlled manifest JSON and on-disk file bytes; malformed input MUST fail safe (preserve, never overwrite) |
| SEC-3 | No | No database patterns |
| SEC-4 | No | No frontend files |
| SEC-5 | Yes | Ownership hashes are the authorization basis for overwrite/delete — hash forgery via crafted manifest is the threat to bound |
| SEC-6 | No | No API/route files |
| SEC-7 | Yes | New/changed exception paths (BaseException rollback, per-restore isolation) MUST never swallow the original error silently |
| SEC-8 | No | No dependency manifests |
