## Background

STORY-slim-2026082381e832771d4e 已实现通用 `finish-guard`、完成证据校验、lease/no-progress 边界及各 `project-*` Skill 的 Pre-Final Protocol。但真实 Codex 会话证明，这仍只是模型可跳过的提示词协议：`project-plan` 在明确输出“仍待完成 HLD、Board、重新 lint 和 workflow 完结”后，宿主直接记录 `task_complete`；对应两个 run 仍停在 `spec_linted / in_progress`，且该 turn 没有调用 `finish-guard`。

部署本身并未失败：`~/.codex/skills/project-plan/SKILL.md` 已包含 Pre-Final Protocol。缺口位于 Codex 宿主生命周期——当前 `pactkit-codex` 只部署 skills、rules、AGENTS.md 和 config，不部署 `Stop` hook。Codex 官方 `Stop` hook 可以在 turn 准备结束时返回 `decision: block`，自动注入 continuation prompt。因此本 Story 将既有 Core finish decision 接入真实 Codex `Stop` 事件，使未完成 workflow 无法仅靠一条阶段总结结束，同时保持普通非 PactKit 对话、真实外部 blocker 和人工高副作用边界不受干扰。

## Requirements

### R1: 部署 Codex 原生 Stop Hook (MUST)

`pactkit-codex` MUST 部署同步 `Stop` lifecycle hook 及其可执行 handler，并使用 Codex 当前支持的 `hooks.json` 或 plugin-bundled hook 结构。Hook MUST 从 stdin 读取官方事件字段，包括 `cwd`、`session_id`、`turn_id`、`stop_hook_active` 和 `last_assistant_message`，并只向 stdout 输出合法 JSON。

Hook 的安装路径、命令路径和 manifest 必须由 adapter 统一生成，不得把开发仓库绝对路径写入用户配置。部署 manifest 必须包含 hook 文件 hash 与 capability；升级时使用原子写入和受管合并，不得覆盖用户已有 hooks。

### R2: Active Workflow 必须确定性解析 (MUST)

Stop handler MUST 以事件 `cwd` 定位项目根，再通过 Core 提供的只读接口选择当前 active PactKit run。选择规则必须优先使用已持久化的 session/turn 绑定；仅有一个 active run 时可确定性回退；存在多个无法消歧的 active run 时必须 fail safe 为 `await_user`/诊断提示，不得任意选择，也不得扫描 cwd 之外的 continuation state。

没有 PactKit 项目、没有 active run、run 已 completed 或事件来自不受管的普通对话时，Hook MUST 返回允许结束且不得创建、修改或恢复 workflow。`last_assistant_message` 只能用于诊断，不能覆盖持久化状态。

### R3: Stop 决策必须复用 Core Finish Guard (MUST)

Handler MUST 调用共享 `ContinuationEngine.finish_guard()` 或等价稳定 CLI/API；不得在 adapter 中复制 workflow step、completion evidence 或 blocker 判断。映射必须为：

- `done`：允许 turn 结束；
- `await_user`：允许结束，并保留真实 blocker handoff；
- `continue_current_turn`/`resume_session`：返回 `decision: block`，reason 包含 run ID、workflow、下一安全步骤和机器可读 reason code；
- 状态损坏、validator drift 或未知决策：fail closed，但必须给出可恢复诊断，不得误报完成。

Stop hook 是同步完成门禁，MUST NOT 配置为 async。它不得直接修改 Spec、Board、Git 或业务 artifact。

### R4: 自动续跑必须有界且防递归 (MUST)

当 `stop_hook_active=false` 且 guard 要求继续时，Hook MUST 返回 `decision: block`，让 Codex 创建 continuation prompt。当 `stop_hook_active=true` 时，必须结合 Core 的 attempt、step/evidence digest、owner lease 与 no-progress 状态裁决，不得无条件再次 block。

同一步骤连续无进展、超过最大 attempt、lease 冲突或 handler 自身重复失败时，系统必须转换为结构化 `await_user` 或安全终止诊断；不得形成无限 continuation loop。每次续跑都必须保持同一 run identity，已完成的 create-only 操作和人工副作用不得重放。

### R5: 人工边界和权限语义保持不变 (MUST)

Stop hook MUST NOT 将 `commit`、`archive`、`tag`、`publish`、`release`、`push` 或 PR 等 manual operation 自动授权。finish guard 返回合法 `await_user` 时 Hook 必须允许 turn 结束，让用户提供新授权或外部输入；历史确认不得跨 run 或跨 operation 重用。

Hook 进程必须继承 Codex 当前 workspace/permission boundary，不得提权、访问凭证或启动后台模型调用。

### R6: 安装、信任与能力报告必须真实 (MUST)

CodexDeployer MUST 报告 hook 的安装位置、启用状态和信任要求。由于 Codex 对新增或变化的非 managed hook 按 hash 要求用户 review/trust，部署不得把“文件已写入”标记为“强制续跑已生效”。在 Hook 未启用、未信任、Codex 版本不支持 `Stop` 或真实 smoke test 未通过时，capability 必须保持 `completion_hook=false`、`auto_resume_available=false`。

`pactkit doctor`/部署验证 MUST 区分 `installed`、`trusted/enabled`、`observed firing` 和 `validated continuation`。只有全部成立，Codex adapter 才可声明 host-level guarantee。

### R7: 用户 Hook 配置必须无损合并和卸载 (MUST)

当部署到 `~/.codex/hooks.json` 或项目 `.codex/hooks.json` 时，adapter MUST 只管理带稳定 PactKit identity 的 entry，保留其他插件和用户 handlers 的顺序与内容。重复部署必须幂等；升级只能替换 PactKit-owned entry；卸载只删除 PactKit-owned entry 和无引用 handler，不得删除整个 hooks 文件。

如果目标环境采用 plugin-bundled hooks，package manifest、hook script 和 skills 必须作为同一版本单元部署，且版本兼容门禁必须阻止 Core/adapter 协议不匹配。

### R8: 真实 Codex 宿主 E2E 是完成门 (MUST)

测试 MUST 覆盖纯 handler contract、隔离部署、配置 merge、Core decision 映射和真实 Codex turn。真实 E2E 必须启动受控 Codex session，令测试任务在 Spec/lint 后故意输出“仍待完成 HLD/Board”，验证 `Stop` hook 实际触发、返回 block、Codex 自动续跑同一 run，并最终在 HLD、Board 和 completion checkpoint 完成后允许 `task_complete`。

仅检查生成文件、mock handler、prompt 文本或 transcript fixture 不足以宣告 Story 完成。若 CI 环境不能运行真实 Codex，相关项必须明确保持未验证，不能把 adapter 单测当成 host guarantee。

### R9: 可观测性与安全失败 (MUST)

每次 Hook 执行必须记录非敏感 decision trace：event/turn/session 的不可逆引用、run ID、workflow、step、decision、reason code、attempt、duration 和 hook version。日志不得保存完整 prompt、`last_assistant_message`、凭证或任意 evidence payload。

stdin JSON 无效、cwd 不可信、project root 不存在、Core CLI 不兼容、timeout 或 stdout 序列化失败时必须产生稳定诊断。任何输出必须符合 Codex Hook schema，避免因格式错误导致 Hook 被跳过。

## Acceptance Criteria

### AC1: 未完成 Plan 被 Stop Hook 自动续跑 (R1, R3, R8)

- **Given** `project-plan` run 停在 `spec_linted` 且 HLD/Board 未完成
- **When** Codex 准备以“仍待完成 HLD、Board”结束 turn 并触发 `Stop`
- **Then** Hook 返回 `decision: block` 和下一安全步骤，Codex 创建 continuation prompt，同一 run 继续而不是记录最终完成

### AC2: 完成或真实 Blocked 正常结束 (R3, R5)

- **Given** run 分别为 completion-validated `completed` 和带合法外部 blocker 的 `blocked`
- **When** Stop handler 调用 finish guard
- **Then** 两者分别按 `done`/`await_user` 允许结束，Hook 不伪造继续、不跨越人工边界

### AC3: 普通 Codex 对话不受影响 (R2)

- **Given** cwd 不是 PactKit 项目，或项目没有 active workflow run
- **When** 任意普通 Codex turn 触发 Stop
- **Then** Hook 允许结束，不创建 continuation state，不根据消息文本误判为 PactKit workflow

### AC4: 多 Active Run 不任意绑定 (R2)

- **Given** 同一项目存在两个 active run，且 session/turn 均无唯一绑定
- **When** Stop handler 解析当前 workflow
- **Then** 返回可诊断的歧义结果并请求用户选择，不得按文件时间、Story 名或最后 assistant 文本猜测

### AC5: 二次 Stop 无进展时不会无限循环 (R4)

- **Given** `stop_hook_active=true` 且 step/evidence digest 与上次相同，已达到 no-progress/attempt 门槛
- **When** Stop 再次触发
- **Then** Core 将状态转为安全 handoff，Hook 不再无条件 block，并输出稳定 reason code

### AC6: 用户 Hooks 无损合并 (R1, R7)

- **Given** `hooks.json` 已有多个用户和插件 handlers
- **When** 首次部署、重复部署、升级及卸载 PactKit Hook
- **Then** 只有稳定标识的 PactKit entry 发生预期变化，其他内容字节语义等价，重复部署不产生重复 handler

### AC7: 未信任 Hook 不宣称生效 (R6)

- **Given** Hook 文件已部署但 Codex 尚未信任其当前 hash
- **When** 查询 deploy manifest、capability 和 doctor
- **Then** 显示 installed 但未 validated，`auto_resume_available=false`，并给出 `/hooks` review 指引

### AC8: 真实宿主验证后才升级保证等级 (R6, R8)

- **Given** 已安装并信任 Stop hook
- **When** 真实 Codex smoke/E2E 观察到 Stop firing、block、自动 continuation 和最终 done
- **Then** 保存非敏感验证证据，capability 才报告 `completion_hook=true` 与 host-level guarantee

### AC9: Hook 故障安全且输出合法 (R3, R9)

- **Given** stdin 损坏、cwd 越界、Core 版本不兼容或 handler timeout
- **When** Stop hook 执行
- **Then** 不修改 workflow/artifact、不泄露 payload，输出合法 JSON 或稳定错误路径，并在 doctor 中可诊断

### AC10: Done 的提前总结也被拦截 (R3, R8)

- **Given** `project-done` 已完成审计但仍待治理刷新、归档、部署或经授权的提交
- **When** agent 发送阶段总结准备结束
- **Then** Stop hook 依据持久化 run 返回继续；只有完成证据通过或真实人工边界出现时才允许结束

## Target Call Chain

```text
Codex model emits final candidate
  → Codex Stop lifecycle event (cwd/session_id/turn_id/stop_hook_active)
  → PactKit Codex stop_handler
      → resolve trusted project root
      → resolve session-bound active workflow run
      → Core HostContinuationRunner.after_model_turn()
          → ContinuationEngine.finish_guard()
          → workflow-specific validator + fingerprints
          → lease / attempt / no-progress policy
      → map decision to Codex Hook JSON
          ├─ continue_current_turn/resume_session → decision:block → continuation prompt
          ├─ done                               → allow Stop
          └─ await_user                         → allow Stop with handoff
```

## Technical Design

### Archaeology and capability delta

Codegraph selected the configured provider with a fresh index. Core 已有 `ContinuationEngine.finish_guard()`、`HostContinuationRunner.after_model_turn()`、lease、attempt 和 no-progress 处理；`pactkit-codex.CodexDeployer.deploy()` 当前只写 skills、rules、AGENTS.md、config 和 manifest，`continuation_capabilities()` 也明确报告 `completion_hook=false`。因此 capability delta 是 Codex lifecycle adapter、run/session 绑定和部署验证，不是新的 workflow engine。

Codex 官方 Hooks 文档确认：`Stop` 事件携带 `cwd`、`session_id`、`turn_id`、`stop_hook_active` 和最后消息；同步 handler 返回 `decision: block` 会让 Codex 创建 continuation prompt。非 managed hook 在首次安装或 hash 变化后需要用户 review/trust，必须纳入能力状态机。

### Lateral Scan Results

- Operation: host turn-completion enforcement。
- Existing implementations: Core 中 1 套通用 finish/host continuation 实现；Codex adapter 中 0 套 Stop hook。
- Assessment: 复用 Core decision contract，在 Codex adapter 增加薄 hook；不得复制 step registry、validator 或 continuation store。

### Hook packaging and ownership

首选将 Hook 与 Codex adapter 作为版本化 plugin unit 打包；若当前 pip deploy 仍写用户级 `~/.codex`，则使用带稳定 owner ID 的增量 `hooks.json` entry。Hook command 指向 adapter 已安装的稳定 executable/module，而不是源码 checkout。Manifest 记录内容 hash、Core protocol version 和 trust/observed 状态。

### Run binding

仅靠 cwd 无法在多个 active run 中安全选择。Core 应提供 session binding/active-run query，将 Codex `session_id/turn_id` 与 workflow run 以非敏感引用持久化。Hook 不读取 transcript 推断 Story，不将消息自然语言作为权威状态。旧 run 无绑定时，仅在唯一 active run 条件下兼容回退。

### Failure and concurrency

Hook 必须同步、快速、只读到决策边界。续跑状态更新通过 Core lock/lease 完成。`stop_hook_active` 不是唯一防循环信号，还必须比较持久化 step/evidence digest 与 attempt。Hook timeout、Core incompatibility 和损坏状态写入最小诊断，绝不直接执行剩余业务操作。

## Out of Scope

- 为 Claude Code、OpenCode 或 Copilot 仿造 Codex `Stop` hook；各平台需使用各自原生 lifecycle。
- 仅靠继续强化 Skill prompt 解决提前 final。
- 自动批准 commit、archive、tag、publish、release、push 或 PR。
- 从 transcript 自然语言猜测 Story/run 身份。
- 在 Hook 未信任或真实 Codex E2E 未通过时宣称 host-level guarantee。
- 引入云端 scheduler、后台模型服务或第二套 workflow 状态库。
