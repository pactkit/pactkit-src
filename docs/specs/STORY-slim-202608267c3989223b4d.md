## Background

Full-codebase review (2026-08-26) of the WorkUnit engine and
continuation store found availability and durability defects. Line
references verified on the working tree; fingerprint validator
cross-checked (receipts accept the literal "missing" at
workflow_engine.py:656 while the state validator at :1046 requires
strict 64-hex — the mismatch is the brick mechanism below).

1. **Permanently bricked run via "missing" fingerprint**
   (workflow_engine.py:2382 region): on submit acceptance the state
   stores _fingerprint(...) which returns "missing" for non-files; the
   external file may vanish between the receipt check and the state
   write (the engine lock serializes state, not the working tree).
   Every later _read of that run fails _validate_workflow_state
   (invoked via :1323) forever — no recovery path.
2. **One corrupt sibling run file blocks the whole engine**
   (workflow_engine.py:1814-1858): _find_run_for_unit and companions
   iterate run files through _read_scanned_state which RAISES on any
   malformed file; a single corrupt unrelated run-*.json fails every
   submit/renew/retry/reject/expire and every story-bound start.
3. **Windows crash**: continuation.py:70 imports fcntl
   unconditionally for engine run locks, while the legacy _story_lock
   (:840 region) has an msvcrt branch — all engine mutation paths die
   with ModuleNotFoundError on Windows.
4. **bind_story TOCTOU** (continuation.py:241-269): the cross-run
   story-uniqueness check holds only the current run's lock; two
   concurrent binds for different runs pass the check and both bind
   the same story.
5. **Transient git failure produces false drift**
   (continuation.py:1141 region): _stale_reasons tolerates
   expected == "unavailable" but not current == "unavailable" — a
   transiently failing git probe during resume reports "worktree
   fingerprint changed".
6. **Raw KeyError/ValueError escape on disk-loaded state**
   (continuation.py:279/284/312/550, host_continuation.py:190):
   direct state indexing on JSON from disk; valid-JSON-but-incomplete
   files surface as bare KeyError instead of ContinuationError.

## Requirements

### R1: A vanished artifact must not brick the run (MUST)

A submit whose artifact disappears between receipt validation and
state persistence MUST fail the submit with an explicit
artifact-vanished error; the literal "missing" MUST NOT be persisted
into state fingerprints (equivalently: state and receipt fingerprint
validators MUST accept the same value set). Existing valid runs MUST
remain readable after the fix.

### R2: Corrupt sibling run files are isolated (MUST)

Scan-based lookups (_find_run_for_unit, _active_runs_for_story,
_completed_run_for_story) MUST skip malformed run files with a warning
instead of raising. Fail-closed semantics are preserved for the TARGET
run: a malformed target run still errors explicitly.

### R3: Engine locks work on Windows (MUST)

The engine run lock MUST use the same platform-split as _story_lock
(fcntl on POSIX, msvcrt on Windows), importing lazily per platform.

### R4: bind_story uniqueness under concurrency (SHOULD)

The cross-run story-binding check SHOULD hold a shared story-level lock
(or post-write revalidate under the store lock) so two concurrent binds
cannot both succeed for the same story_id.

### R5: Transient git unavailability is not drift (SHOULD)

_stale_reasons SHOULD treat current == "unavailable" as
inconclusive-with-retry rather than a fingerprint change.

### R6: Disk-state access errors are typed (SHOULD)

Direct state key access on JSON loaded from disk SHOULD be guarded so
that structurally-invalid records raise ContinuationError with the
offending file named, not bare KeyError/ValueError.

## Acceptance Criteria

### AC1: vanished artifact fails submit, run stays readable (R1)

- **Given** a run mid-submit whose artifact file is deleted after receipt validation (simulated by monkeypatched unlink between the two calls)
- **When** submit completes
- **Then** the submit fails with an artifact-vanished error AND a subsequent read of the run succeeds

### AC2: corrupt sibling does not block unrelated operations (R2)

- **Given** a store with one valid run and one corrupt run file
- **When** submit/status is invoked for the valid run's unit
- **Then** the operation succeeds and a warning names the corrupt file

### AC3: malformed target run still errors (R2)

- **Given** a corrupt run file that IS the target of the operation
- **When** submit/status targets it
- **Then** an explicit invalid-state error is raised (not a silent skip)

### AC4: Windows lock path imports (R3)

- **Given** os.name == "nt" (simulated via monkeypatch)
- **When** the engine run lock is acquired
- **Then** no fcntl import is attempted and the msvcrt branch is selected

### AC5: concurrent binds cannot both succeed (R4)

- **Given** two threads binding different runs to the same story_id with interleaved execution (simulated via lock-release hooks)
- **When** both bind_story calls complete
- **Then** exactly one binding succeeds and the other raises the duplicate-active-run error

### AC6: unavailable current fingerprint is not drift (R5)

- **Given** a checkpoint holding a real digest and a git probe returning "unavailable"
- **When** _stale_reasons evaluates
- **Then** no worktree-drift reason is emitted
