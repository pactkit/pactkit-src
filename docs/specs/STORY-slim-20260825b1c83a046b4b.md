## Background

PactKit 2.23.0 已将一个常驻规则文件部署到宿主全局规则目录，并将七个操作规则及十九个工程 guide 部署到 skill 私有目录。命令通过 `COMMAND_RULES_MAP` 和阶段内条件读取组合这些内容。这个“常驻 + 按需”的方向正确，但职责边界仍然混乱：常驻 `pactkit.md` 同时包含 session、TDD、可视化、模型选择、真相层级、File Atlas、完整命令手册和工程原则；按需规则又与 skill playbook 重复；engineering guides 中大量 MUST/NEVER 被误用为所有项目的硬约束。

实际使用中，这种混合会让流程治理覆盖可用性：普通 coding 被 PDCA 接管，历史 workflow/run 状态限制当前安全工作，用户被要求切换 session，Claude Code 输出 Codex runner/WorkUnit 术语，过期测试或缺失 evidence 被升级成永久阻塞。与此同时，`~/.claude/rules/` 还包含用户自有的安全、skill discovery、design routing 和 operational discipline 文件；PactKit 不得将这些文件误认为产品规则或在升级时覆盖。

本 Story 将规则系统重构为场景驱动的分层架构。常驻层只保护安全、授权和当前会话可用性；PDCA 质量约束随对应 skill 激活；engineering guides 按风险触发并默认为可解释建议；只有安全、权限和不可逆损坏风险能够阻止继续工作。缺少阶段证据只能阻止“声称完成”，不能阻止继续调查、实现、测试和修复。

### Current Reality

- `src/pactkit/prompts/rules.py` 将 `core + hierarchy + atlas + routing + principles + nudge` 合并为始终加载的 `pactkit.md`。
- `RULES_ONDEMAND_FILES` 将 workflow、MCP、shared、architecture、sectional、solution、engineering 部署至 `skills/_rules/`。
- `COMMAND_RULES_MAP` 决定各 `project-*` command 的静态 imports；Act/Plan 还在 phase 内条件读取 solution 和 engineering guides。
- `src/pactkit/generators/deployer.py::_deploy_rules` 负责全局与按需目录路由和旧文件清理；`_build_command_rules_header` 按宿主 profile 选择 `@import`、inline 或 instructions。
- `src/pactkit/deploy_manifest.py` 以部署文件 hash 记录 PactKit ownership，但旧文件清理仍依赖源码中的 filename 集合。
- `src/pactkit/prompts/guides.py` 含有“所有缓存必须 TTL”“每个 awaitable 必须 timeout”“事务不得超过一秒”等脱离场景的绝对规则。
- Act 已支持 Spec Input Preflight，但其失败语义和其他 phase gates 仍含 `STOP` 式提示，未统一遵循非阻塞完成语义。

## Goals

1. 建立可解释、可测试、跨宿主一致的 PactKit 规则分层模型。
2. 让普通对话、普通 coding、各 PDCA phase、UI design 和 PactKit self-development 只加载所需规则。
3. 将阻塞能力限制到安全、权限、不可逆损坏和无法安全推断的实质歧义。
4. 保留 Spec、TDD、验证证据和工程治理，但将失败限制为对应阶段的完成门禁。
5. 严格分离 PactKit-owned、project-owned 和 user-owned 文件，保证升级和卸载无损。
6. 在 Claude Code、Codex、OpenCode 及其他 adapter 中保持相同语义，同时使用各宿主的自然术语。

## Rule Architecture

| Layer | Owner | Load policy | Responsibility |
|-------|-------|-------------|----------------|
| L0 Host safety and authority | Host/User | 始终有效 | 平台安全、工具权限、外部副作用授权 |
| L1 PactKit Runtime Kernel | PactKit | 始终加载 | 当前 session、非阻塞、语言匹配、skill 激活边界 |
| L2 Phase Contract | PactKit skill | 仅当前 command | Plan/Act/Check/Done/PR/Release/Hotfix 阶段契约 |
| L3 Shared Capability Module | PactKit skill | command 显式引用 | preflight、external tools、shared execution、Git workflow |
| L4 Concern Guide | PactKit | Spec/代码风险触发，通常 1–3 个 | 风险决策表、默认策略和可验证注意项 |
| L5 Maintainer Overlay | Project | 仅 PactKit 仓库 | PactKit 源码、adapter parity、prompt budget 等维护约束 |
| L6 Personal Preference | User | 用户配置决定 | safety、skill discovery、design routing、个人操作偏好 |

## Rule Semantics

每个可执行规则模块 MUST 声明或可确定以下元数据语义：

```yaml
id: ACT-PREFLIGHT-001
owner: pactkit
level: required
scope: project-act
trigger: before_first_source_write
skip_when:
  - no_spec_reference
  - project-hotfix_active
evidence:
  - matching_preflight_receipt
failure: incomplete_continue
override: user_can_override_with_reason
```

| Level | Meaning | Permitted failure behavior |
|-------|---------|----------------------------|
| `hard` | 安全、凭据、权限或重大不可逆损坏边界 | `block_action` |
| `required` | 宣布当前 phase 完成所必需的证据 | `incomplete_continue` |
| `default` | 有证据时应采用的推荐路径 | `record_deviation` |
| `advisory` | 提醒和设计参考 | `warn_continue` |

`MUST`/`NEVER` 只有在元数据为 `hard` 或 `required` 且作用域明确时才可使用。`SHOULD` 表示可基于项目证据偏离，不得强制向业务源码写入 `DEFERRED` 注释。

## Precedence

冲突按以下顺序解决：

1. 平台安全、工具权限和凭据保护。
2. 用户在当前对话中的最新明确指令与授权。
3. 项目的 `AGENTS.md`、`AGENTS.local.md` 和项目配置。
4. 当前激活的 command、已确认 Spec 和 Test Case。
5. PactKit Runtime Kernel。
6. 按需加载的 engineering guide。
7. 用户默认偏好、示例和模板。

用户指令 MAY 覆盖流程偏好，但 MUST NOT 覆盖平台安全。用户确认的需求变化高于旧 Spec；执行方应更新或标注旧 Spec，而不是继续实施已知过期内容。

## Requirements

### R1: 最小常驻 Runtime Kernel (MUST)

PactKit MUST 将始终加载的 `pactkit.md` 精简为独立 Runtime Kernel，只包含 activation、current-session execution、user authority、rule semantics、failure handling、language matching 和 skill loading。它 MUST NOT 包含完整 command 手册、File Atlas、全局 Strict TDD、Visual First、固定模型名/成本、Git/Release 细节或通用 engineering guide。

### R2: 显式场景与 Phase Contract (MUST)

每个 `project-*` skill MUST 只加载自身 phase contract 及显式声明的共享模块。没有激活 PactKit command 的普通问答和普通 coding MUST NOT 自动进入 PDCA、加载阶段门禁或要求初始化项目。`project-sprint` MUST 在当前宿主 session 内顺序组合 phase contract；新 session 只能作为用户选择。

### R3: 非阻塞执行策略 (MUST)

实现 MUST 采用本 Spec 的 `hard/required/default/advisory` 语义。只有未获授权的外部副作用、凭据泄露、不可逆损坏风险和无法安全推断的重大歧义 MAY 阻止当前操作。历史 run、WorkUnit、journal、receipt、Board、continuation、旧 phase 或缺失的推荐 evidence MUST NOT 成为当前安全工作的排他锁。`required` 失败 MUST 只阻止完成声明，并给出可继续执行的下一步。

### R4: 宿主原生执行语言 (MUST)

部署到 Claude Code、Codex、OpenCode 和其他 adapter 的规则与 commands MUST 使用当前宿主的自然执行模型。Claude Code 输出 MUST NOT 指示“运行 codex runner”“owner codex”“派发 WorkUnit 到 Codex 线程”或要求换 session。Portable workflow records MAY 作为可选恢复证据，但 MUST NOT 暴露为用户必须操作的宿主无关编排。

### R5: Phase Failure Classification (MUST)

Plan、Act、Check、Done MUST 共享失败分类：当前改动回归、pre-existing failure、obsolete contract/test、environment/dependency failure。可安全继续时 MUST 继续作用域内工作。Act 的 Spec lint、Spec preflight、TDD、regression 和 lint 失败 MUST 返回可操作诊断；除 `hard` 风险外，不得形成永久 workflow lock。pre-existing failure MUST 先建立因果关系，不能一律禁止修改测试或相关实现。

### R6: Risk-driven Engineering Guides (MUST)

Engineering guide MUST 从“全局绝对规范”重写为“触发条件 + 决策表 + hard safety + defaults + evidence”。Plan/Act 每次 SHOULD 加载 1–3 个与 Spec concern 匹配的 guide，不得全量注入。除安全不变量外，缓存 TTL、idempotency key、health endpoint、事务时长、awaitable timeout、事件驱动阈值等 MUST 表达为依赖场景的 default/advisory，而不是无条件硬门禁。

### R7: Ownership 与无损部署 (MUST)

PactKit MUST 只创建、更新、迁移或删除 manifest 明确记录为 PactKit-owned 的文件。`~/.claude/rules/10-safety.md`、`13-skill-discovery.md`、`14-design-skill-routing.md`、`slim-01-operational-discipline.md` 及其他 user-owned 文件 MUST 保持独立且不得被 deploy/update/uninstall 覆盖。升级遇到用户修改过的 PactKit-owned 文件时 MUST 保留用户版本并报告 diff/conflict，或生成 side-by-side 候选；不得静默覆盖。

### R8: 文件与模块职责重构 (MUST)

规则源码和部署结果 MUST 明确表达以下职责，具体文件名 MAY 按宿主 profile 映射，但逻辑身份必须稳定：

- `pactkit-runtime`: 最小常驻内核。
- `phases/*-contract`: Plan、Act、Check、Done、PR、Release、Hotfix 阶段契约。
- `execution/shared-execution`: 通用执行与失败分类。
- `execution/spec-preflight`: Spec 引用读取和 receipt 语义。
- `execution/external-tools`: MCP/外部工具的条件使用。
- `design/capability-design`: 框架能力差距评估。
- `engineering/index` 与 `engineering/guides/*`: concern router 和按需 guides。
- `maintainer/pactkit-maintainer`: 仅 PactKit self-development 使用。

Command reference MUST 以 skill 本身为单一事实源；File Atlas MUST 移至 project-local instructions/profile，不在全局 runtime 中复制。Sectional Write MUST 降级为宿主编辑 heuristic，不能成为项目工程 Law。

### R9: Rule Registry 与静态校验 (MUST)

PactKit MUST 提供单一规则注册表，记录逻辑 ID、owner、level、scope、load policy、部署路径和允许的 failure behavior。构建或测试 MUST 校验：引用的 rule 存在、每个 phase import 合法、`hard` 规则只使用允许的 blocker 类别、guide 不被常驻加载、user-owned 文件不进入 managed set、旧 filename migration 有明确映射。

### R10: 跨 Adapter 语义一致性 (MUST)

Classic/Claude 的 `@import`、OpenCode/Copilot 的 inline、Codex 的 instructions/skill 机制 MUST 从同一逻辑注册表渲染。格式差异 MAY 改变路径和语法，但 MUST 保持 activation、priority、blocking、ownership 和 completion semantics 一致。Parity tests MUST 检测规则丢失、重复注入、常驻泄漏、宿主术语污染和 adapter version incompatibility。

### R11: 兼容迁移与回滚 (MUST)

从 2.23.0 升级时 MUST 将现有 `pactkit.md` 和 `01-` 至 `07-` 按需规则迁移到新架构，清理仅限已知 PactKit-owned legacy paths。配置中的 `rules`、`rule_scopes` 和 `command_rules` MUST 获得显式迁移或兼容解释，不得静默改变用户选择。迁移 MUST 幂等；失败时 MUST 保留最后一个完整部署及 manifest，使用户可继续使用旧规则。

### R12: 可用性与上下文预算 (SHOULD)

Runtime Kernel SHOULD 控制在 70 行以内；单个 phase contract SHOULD 只描述该 phase 的不变量，不复制操作手册；同一 command 的静态规则文本 SHOULD 相比 2.23.0 减少。偏离这些预算时，测试或设计记录 MUST 给出原因，不得在产品源码中插入 `DEFERRED(SHOULD)` 注释。

### R13: Personal Rules 的友好协作 (SHOULD)

PactKit SHOULD 提供只读 doctor/audit 输出，区分 PactKit-owned、project-owned、user-owned 规则，并提示个人规则中可能与当前 phase contract 冲突的条款。它 MUST NOT 自动改写个人规则。用户点名 skill 时，个人 design routing 只能作为未指定情况下的 default；skill discovery 不得自动安装或无条件联网；release discipline 仅在 Release 场景生效。

## Technical Design

### Lateral Scan Results

- Operation: 规则定义、按 command 选择、跨宿主渲染和 managed-file ownership。
- Existing implementations: `RULES_MODULES`/`RULES_FILES`（内容与文件身份）、`COMMAND_RULES_MAP`（命令选择）、`_get_command_rules`/`_build_command_rules_header`（加载与渲染）、`_deploy_rules`/`_deploy_guides`（落盘）、`collect_owned_files`（manifest ownership），共五处独立但互相关联的映射。
- Assessment: 提取统一 Rule Registry 作为共享抽象是必要的；各宿主 adapter 只保留路径和导入语法转换，不再复制规则语义。现有 `RULES_*` 常量保留为一个 minor version 的兼容投影，避免一次性破坏 adapter。

### Logical Registry

引入结构化 registry 作为规则身份和加载关系的单一事实源，渲染层继续输出各宿主可消费的 Markdown：

```python
RuleDefinition(
    id="runtime",
    owner="pactkit",
    level="hard",
    scope=("global",),
    load_policy="always",
    source_key="runtime",
    relative_path="rules/pactkit-runtime.md",
    failure_behaviors=("block_action", "warn_continue"),
)
```

Phase contracts和共享模块由 command dependency graph 引用。Deployer 根据 profile 将逻辑路径转换为 `~/.claude/rules`、`~/.claude/skills/_rules`、`~/.codex/rules` 或 inline instructions。Manifest 记录逻辑 ID、owner、目标路径、content hash 和 schema version，而不是仅靠 filename 猜测 ownership。

### Activation Model

```text
User task
  ├─ no PactKit skill active → Runtime Kernel only
  └─ PactKit skill active
       ├─ phase contract
       ├─ declared shared capabilities
       └─ Spec concerns → 0..3 engineering guides

Completion decision
  ├─ hard violation → block exact risky action
  ├─ required evidence missing → continue work, completion=false
  ├─ default deviation → record rationale, continue
  └─ advisory → report when useful, continue
```

### Preflight Receipt

Spec preflight receipt MUST 绑定 `project_root`、`spec_path`、`spec_hash`、`command`、时间和引用文件 hash，保存到项目本地 `.pactkit/preflight/`。Guard 只在 Act 已激活、首次写源码、当前 Spec 有引用且 receipt 不匹配时介入。默认失败应给出一条可执行修复命令；工具自身故障或用户显式 override 时降级为 warning 并记录原因，不能永久锁死。

### Migration Strategy

1. 先加入 registry 和兼容别名，保持 2.23.0 的目标路径可读。
2. 将 Runtime Kernel 内容缩减，并新增 phase/shared/maintainer 模块。
3. 让 command dependency graph 从 registry 生成 imports。
4. 重写 guides 的等级和触发语义。
5. 在临时 HOME/target 中执行旧版 manifest 到新版 manifest 的迁移测试。
6. parity 全绿后才移除旧模块 key；至少保留一个 minor version 的诊断映射。

## Acceptance Criteria

### AC1: 普通任务不激活 PDCA (R1, R2)

- **Given** 一个未调用 `project-*` skill 的普通问答或代码修改请求
- **When** 宿主加载 PactKit 全局规则
- **Then** 上下文只包含 Runtime Kernel，不出现 TDD、Visual First、Board、WorkUnit、初始化或 phase gate 指令，也不要求用户换 session

### AC2: Act 精确加载规则 (R2, R6, R8)

- **Given** 用户调用 `project-act`，Spec 只声明 database 和 resilience concerns
- **When** command rules 被解析和渲染
- **Then** 加载 Runtime、Act contract、shared execution、spec preflight、database 和 resilience guides，不加载 Plan/Release contracts 或其余 guides

### AC3: Required gate 不形成永久锁 (R3, R5)

- **Given** Act 的 preflight receipt 缺失、历史 run 已 blocked 或 regression 中存在未确认因果的旧失败
- **When** 用户继续调查、补 receipt、修复实现或运行测试
- **Then** PactKit 允许所有安全的当前作用域操作，只将 phase completion 标记为未满足，并返回具体下一步

### AC4: Hard gate 精确阻断风险动作 (R3)

- **Given** 未授权的 release/push、凭据写入或项目根目录外的破坏性写入
- **When** 对应动作将被执行
- **Then** 只阻断该风险动作，说明原因和所需授权；不冻结无副作用的阅读、诊断和本地修复

### AC5: Claude Code 不出现 Codex 编排术语 (R4)

- **Given** Core rules/commands 部署到隔离的 Claude Code target
- **When** 对全部部署文本执行语义扫描
- **Then** 不存在 `codex runner`、`--owner codex`、`Codex thread` 或“必须新 session”指令；恢复能力以 Claude Code 当前 session 的自然语言表达

### AC6: Personal Rules 无损 (R7, R13)

- **Given** target 的 `rules/` 含四个用户自有文件及一个被用户修改的 PactKit-owned 文件
- **When** 执行 update、迁移及 uninstall 测试
- **Then** 用户文件 byte-for-byte 不变；修改过的 managed 文件不被静默覆盖；doctor 清楚报告 owner、hash drift 和可选处理方式

### AC7: Guide 风险驱动语义 (R6, R9)

- **Given** 十九个 engineering guides
- **When** registry validator 和内容测试运行
- **Then** 每个 guide 声明 trigger、defaults、hard safety 和 evidence；不存在被误定义为通用 hard rule 的 TTL、幂等键、health endpoint、一秒事务、全 awaitable timeout 或固定 event-driven 阈值

### AC8: 跨 Adapter parity (R10)

- **Given** 同一规则 registry 分别部署为 classic、codex、opencode 和 copilot 格式
- **When** parity verifier 归一化各格式的逻辑 rule IDs、levels、scopes 和 failure behaviors
- **Then** 四个结果完全一致，且每个 adapter 只使用自身支持的 import/instruction 机制和宿主术语

### AC9: 2.23.0 无损迁移和回滚 (R7, R11)

- **Given** 一个包含 2.23.0 manifest、当前 `pactkit.md`、`01-` 至 `07-` rules、guides、用户文件和自定义 `command_rules` 的隔离 target
- **When** 连续执行两次新版 update，并模拟一次中途写入失败
- **Then** 成功路径幂等且保留配置语义；失败路径保留最后一个完整部署；清理仅命中 manifest/legacy map 中的 PactKit-owned 文件

### AC10: Runtime 与上下文预算 (R1, R12)

- **Given** 新 Runtime Kernel 和每个 command 的归一化渲染文本
- **When** prompt budget tests 与 2.23.0 baseline 比较
- **Then** Runtime Kernel 不超过 70 行，且普通任务常驻 PactKit 文本显著减少；任何 command 文本增长都有测试中的明确理由

### AC11: Precedence 可判定 (R3, R9)

- **Given** 旧 Spec、用户当前明确变更、项目本地指令和 advisory guide 相互冲突
- **When** rule resolver 评估优先级
- **Then** 在不违反平台安全的前提下采用用户当前决定和项目本地约束，标注旧 Spec 待同步，并忽略冲突的 advisory，而不是停止整个 workflow

### AC12: PactKit self-development 隔离 (R8)

- **Given** PactKit 仓库与一个普通业务仓库
- **When** 相同 phase skill 分别激活
- **Then** `pactkit-maintainer` overlay 只在 PactKit 仓库加载，adapter parity 和 prompt budget 等维护约束不出现在业务项目上下文
